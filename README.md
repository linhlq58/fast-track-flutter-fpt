# Day 26 – Hive/SharedPreferences (Concept/Lecture, 90 mins)

1. Why Local Storage? (≈10 mins)
Apps need data to survive restarts and, in some cases, work without a network: login session, user settings, cached API responses, drafts
Link to Day 23: when a request fails, showing cached data is often better than an error screen
Intermediate expectation: choose the right storage for the type of data, and keep storage code in the data layer (never inside widgets)
Storage options at a glance:
SharedPreferences: small key-value settings (theme, onboarding flag, last selected tab)
Hive: fast NoSQL key-value/box database for structured objects and cached lists
SQLite (sqflite/drift): relational data, complex queries (mention only, out of scope)
flutter_secure_storage: tokens and secrets (mention only; never store tokens in SharedPreferences or plain Hive)

2. SharedPreferences (≈20 mins)
Stores primitives only: int, double, bool, String, List<String>
 
```dart
final prefs = await SharedPreferences.getInstance();   
await prefs.setBool('isDarkMode', true);  
final isDark = prefs.getBool('isDarkMode') ?? false; // null safety (Day 1)   
await prefs.remove('isDarkMode');
```

Platform backing: NSUserDefaults on iOS, SharedPreferences on Android
Best practices:
Define keys as constants (avoid typos in string keys)
Always provide defaults with ??
Wrap it in a small class so the rest of the app does not depend on the package:
 
```dart
class SettingsStorage {      
    final SharedPreferences _prefs;      
    SettingsStorage(this._prefs);       
    static const _darkModeKey = 'isDarkMode';      
    bool get isDarkMode => _prefs.getBool(_darkModeKey) ?? false;      
    Future<void> setDarkMode(bool value) => _prefs.setBool(_darkModeKey, value);    
}
```

Limitations: no complex objects, no queries, not meant for large data, not encrypted

3. Hive (≈30 mins)
Concepts: a Box is like a table/map persisted on disk; data is stored as key-value pairs
Setup and basic CRUD (with a plain Map/JSON, no adapters):
 
```dart
await Hive.initFlutter(); // in main(), before runApp  
final box = await Hive.openBox('posts_cache');
await box.put('posts', jsonEncode(postsJson)); // create/update  
final raw = box.get('posts') as String?; // read  
await box.delete('posts'); // delete  
await box.clear(); // clear the box
```

Storing typed objects with TypeAdapters:
 
```dart
@HiveType(typeId: 0)  
class PostModel extends HiveObject {    
    @HiveField(0)    
    final int id;    
    
    @HiveField(1)    
    final String title;     
    
    PostModel({required this.id, required this.title});  
}   

Hive.registerAdapter(PostModelAdapter());   // generated by hive_generator  
final box = await Hive.openBox<PostModel>('posts');  
await box.put(1, PostModel(id: 1, title: 'Hello'));
```

Generated with dart run build_runner build (same workflow as freezed on Day 21)
Trade-off to discuss: JSON string in a box (simple, reuses existing fromJson/toJson, easier migration) vs TypeAdapters (faster, typed, but needs typeId management and migration care). Course lab recommends the JSON approach for simplicity
Pitfalls:
Forgetting await Hive.initFlutter() or opening a box twice with different types
Changing @HiveField indexes later, which corrupts existing data
Not closing/opening boxes consistently
Note for trainer: check the package’s current maintenance status before the course, since alternatives such as Isar, ObjectBox, or drift may be preferred in new projects

4. Caching Strategy for Offline Scenarios (≈20 mins)
Basic cache-then-network flow inside the repository:
 
```dart
Future<List<Post>> getPosts() async {    
    try {      
        final posts = await _remote.fetchPosts();     // Dio call (Day 21)      
        await _local.cachePosts(posts);               // save to Hive      
        return posts;    
    } on AppFailure {                               // Day 23 failures      
        final cached = await _local.getCachedPosts();      
        if (cached.isNotEmpty) return cached;         // fall back to cache      rethrow;                                      // nothing cached: surface the error    
    }  
}
```

Key design questions:
Cache invalidation: when is cached data too old? Store a timestamp and apply a simple TTL (e.g., 10 minutes)
Source of truth: network-first (fresh data preferred, cache as fallback) vs cache-first (instant UI, then refresh)
UI feedback: tell the user when data is from cache (e.g., “Offline - showing saved data”)
Connect to Day 15 and Day 23: the Bloc calls the repository and does not know where the data came from; error and empty states still apply
